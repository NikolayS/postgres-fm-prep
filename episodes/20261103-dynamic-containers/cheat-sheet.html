Dynamic containers · cheat sheet

Postgres.FM · guest Álvaro Hernández (OnGres, StackGres, DOCIR) · full brief and animations

Every Postgres deployment has to add its extensions to the server image at some point. Approaches differ in when that happens: build, pod start, pull or mount. Álvaro built two of the four, StackGres runtime injection and DOCIR.

The four answers

ApproachComposed atStrengthCost
Fat imagebuild · youSimple; one artifactSize, CVE noise, rebuild and retag per change, 2ⁿ combinations

Key facts

  • extension_control_path (PG 18) is where Postgres looks for .control and SQL files; the default is $system. The .so files are still found through the old dynamic_library_path. That makes two searches.
  • Commit 4f7f7b0375, 2025-03-19. Peter Eisentraut and Matheus Alcantara wrote it; David Wheeler started the thread; Bartolini and the CNPG team reviewed it. The commit message names CloudNativePG as a use case.
  • ImageVolume (KEP-4639): alpha in K8s 1.31; on by default in 1.35; GA in 1.36 according to the KEP file. Needs containerd ≥ 2.1 or CRI-O ≥ 1.31.
  • CNPG mounts each image at /extensions/<name> and appends …/share and …/lib after $system and $libdir. A Database resource runs CREATE EXTENSION.
  • CNPG timeline: 1.27 (Aug 2025) added extensions, 1.29 (Apr 2026) added them to image catalogs. Official images exist only for Debian trixie and bookworm, and only for CNCF-allowlisted licences (PostGIS is grandfathered).
  • CNPG's pgvector image is FROM scratch with only /lib, /share and /licenses. The PostGIS image also copies the system libraries the base lacks into /system, reached through LD_LIBRARY_PATH.

Gotchas to raise

  • "No rebuild" doesn't mean "no restart". With ImageVolume, every add, remove or update is a rolling restart. Changes to ld_library_path, bin_path or env need a manual restart.
  • shared_preload_libraries is still manual.
  • ABI: the image must match the PG major, distro and architecture. PG_MODULE_MAGIC doesn't check glibc.
  • The $libdir landmine: LOAD '$libdir/postgis-3' inside extension scripts bypasses the path search. Bug #19506 was filed in June 2026 and is still open. CNPG works around it by sed-patching PostGIS's SQL.
  • pg_upgrade with extension_control_path was broken until commit 1e67508730 (Mar 2026).
  • Shared native libraries: PostGIS and pgRouting both need GEOS. What happens if the versions differ?

DOCIR in 30 seconds

  • A from-scratch OCI registry. A name:reference maps to a list of layers plus a config, and the manifest is generated per request. Layer metadata is stored in Postgres and blobs in S3. It is multi-arch and uses tokens.
  • Names are URL paths. There is a live, experimental and not yet optimised instance:
docker pull sgcr.dev/postgres docker pull sgcr.dev/postgres/e/vector docker pull sgcr.dev/postgres/e/pgvector/pg_stat_statements/citext # each pull fetches only the additional layers
  • A REST API and a website build these URLs. Ask him what "SGCR" stands for (our guess: StackGres Container Registry).
  • The OnGres post on packaging extensions as OCI images is the research that led to DOCIR. It is not a description of how DOCIR is built.

The debate: DOCIR vs ImageVolume

The case for DOCIR: ImageVolume is Kubernetes-specific, Postgres-specific, PG 18+ only and has no combined SBOM. It is a narrow solution and DOCIR is a general one.

Push back with:

  • Each extension image can carry its own SBOM. Why does an auditor need one combined SBOM?
  • For a Postgres operator, being Postgres-specific is the point. What is the second use case for dynamic images?
  • Is it either/or? Could DOCIR serve what ImageVolume mounts?
  • Is 2ⁿ a strawman? Most users want about 10 combinations.
