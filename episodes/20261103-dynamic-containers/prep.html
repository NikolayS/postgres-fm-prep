Dynamic containers for Postgres

Every Postgres deployment has to combine the server binaries with the extensions it needs. The approaches differ in when that happens: at build time, at pod start, at pull time or at mount time. The episode is a tour of those four answers, with the person who has built two of them.

The case for DOCIR to put to Álvaro: ImageVolume is Kubernetes-specific, Postgres-specific and Postgres 18+ only, and it cannot produce a combined SBOM, which makes it a narrow solution and DOCIR a general one. Let him make the case, then push back with the counter-questions under "The debate" below.

For Álvaro · grouped by segment

Questions

The story

  1. When did StackGres start loading extensions at runtime, and what made you stop baking them in?The StackGres 1.0 (2021) announcement says 120+ extensions. What is the number today?
  2. What failed in production with runtime injection: air-gapped installs, cold starts, the extensions cache?
  3. "Postgres in the Container Era" (2024) → "à la carte" (2025) → DOCIR. What changed your mind between the talks?

DOCIR

  1. Walk us through one pull: reference → layers → manifest. Where does the business logic live, and who writes it?
  2. Is the order of extensions in the tag canonicalised? Is the same combination always the same digest?
  3. How do signing (cosign), SBOMs and pinning by digest work for images that are generated?
  4. Status: open source? License? The slides targeted v1.0 in Q2 2026. Where is it now?

The debate

  1. Kubernetes 1.35 turned ImageVolume on, and CNPG uses it with two GUCs. What does DOCIR still give a Kubernetes user?The expected case: ImageVolume is Kubernetes-specific, Postgres-specific and PG 18+ only, and has no combined SBOM. It is narrow; DOCIR is general. Ask what other reasons he sees.
  2. Counter: each CNPG extension image can carry its own SBOM, and the cluster status lists every image by reference. Why does a single combined SBOM matter to an auditor?
  3. Counter: for a Postgres operator, being Postgres-specific is the point. Who outside Postgres needs dynamic images? Name the second use case.
  4. Either/or? Could DOCIR serve the extension images that ImageVolume mounts, or a composed image that CNPG uses as its operand?
  5. Why not a three-line Dockerfile with apt-get install postgresql-18-postgis-3?
  6. Is 2ⁿ a strawman? Most users want about 10 combinations. Why not pre-build the top 50?

Hard parts

  1. ABI: the image must match PG major, distro and architecture. Is that enough? glibc symbol versions, LLVM bitcode, compiler flags?
  2. Shared native dependencies: PostGIS and pgRouting both want GEOS. What happens when versions differ?
  3. shared_preload_libraries still needs a restart. Is "no rebuild" the real win, rather than "no restart"?
  4. Major upgrades: who guarantees that the same extension version exists for both majors?

Ecosystem

  1. Should extension authors publish OCI artifacts (FROM scratch with /lib and /share) next to debs?
  2. PGXN v2, Trunk, Pigsty, PGDG, CNPG images, StackGres repo: can one OCI media-type spec serve all of them?
  3. Licensing: CNPG accepts only CNCF-allowlisted licences (PostGIS is grandfathered). How does a commercial registry handle GPL extensions?

Nik's angles

  1. Thin clones (DBLab): could a clone boot with a different extension set from production, for example hypopg or plprofiler only on the clone?
  2. And the opposite: how do we prove the clone runs exactly production's extension digests?
  3. Branching for AI agents: a database branch with on-demand extensions, created at pull time?
