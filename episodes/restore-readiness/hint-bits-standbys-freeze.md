# Hint bits, standby reads, and whether to FREEZE

[Host TL;DR](hosts-tldr.md) · [First-read WAL measurements](first-read-writes.md) · [PG19 standby VM behavior](pg19-standby-and-episode-angles.md)

Updated October 20, 2026. Standby behavior here is verified from PG19rc1 source, not a new replication experiment. The existing Forge first-read experiments ran on primaries.

## Three different kinds of readiness

| State | Purpose | Relevant preparation |
| --- | --- | --- |
| Planner statistics | Estimate rows and choose plans | ANALYZE or usable imported statistics |
| Hint bits and all-visible VM coverage | Avoid repeated transaction-status work and unnecessary heap visibility checks | VACUUM; some work may already have happened during index creation/reads |
| Frozen tuples / all-frozen VM coverage | Reduce future transaction-ID freezing work on unchanged data | Ordinary vacuum can freeze too; FREEZE requests aggressive freezing |

All-visible and all-frozen are different. An Index Only Scan needs the all-visible bit; it does not require the all-frozen bit. [Index-only scan mechanism](https://www.postgresql.org/docs/19/indexes-index-only-scans.html), [freezing and wraparound prevention](https://www.postgresql.org/docs/19/routine-vacuuming.html#VACUUM-FOR-WRAPAROUND).

## Standby reads: hints are not the visibility map

PG19's read-time VM path is disabled in recovery; standby VM updates arrive through WAL replay. **This does not mean a standby reader cannot modify tuple hint bits.** Hints cache transaction status and can be established locally when safe. Do not assume identical hint bits on primary and standby.

The exact dirtying rule matters. In `MarkSharedBufferDirtyHint`, for a clean permanent shared buffer:

| Local standby setting | Hint-only clean-to-dirty transition | New WAL generated by standby SELECT |
| --- | --- | --- |
| Checksums off AND wal_log_hints off | Can occur | None |
| Checksums on OR wal_log_hints on | This hint path returns during recovery without marking it dirty | None |

The second case can still set an in-memory hint. Without another reason to persist the buffer, it may be lost on eviction and later recomputed. Already-dirty buffers and changes made by WAL replay are separate; this table does not promise zero dirty buffers or zero disk writes on a standby.

Primary sources: [hint dirtying and recovery guard](https://github.com/postgres/postgres/blob/REL_19_RC1/src/backend/storage/buffer/bufmgr.c#L5738), [XLogHintBitIsNeeded definition](https://github.com/postgres/postgres/blob/REL_19_RC1/src/include/access/xlog.h#L135), [safe hint-bit setting](https://github.com/postgres/postgres/blob/REL_19_RC1/src/backend/access/heap/heapam_visibility.c#L102), [hot standby cannot generate transaction WAL](https://www.postgresql.org/docs/19/hot-standby.html).

**Four separate observations:** an in-memory byte changed; a buffer became dirty; WAL was generated; a page was written to storage. One does not imply all four. EXPLAIN dirtied-buffer counts are not physical write counts.

## Does this strengthen the case for post-restore VACUUM ANALYZE?

**Yes, when predictable first-query behavior matters.** Its value includes moving physical preparation out of application requests, not just improving planner estimates and index-only scans. The measured first count after VACUUM generated no WAL in the Forge fixture; without maintenance, the checkpointed checksummed PG18 case generated about 27 MiB. [Exact controls and limits](first-read-writes.md).

That is an argument for scheduling and verifying preparation, not proof that every restore needs a full manual pass or that total I/O always falls. Index builds or autovacuum may already have done work. Some tables are never queried. Maintenance itself costs I/O/WAL; usable imported stats may reduce the need for analysis. Plain VACUUM need not inspect every page in every state.

Perform maintenance on the primary, then account for WAL replay before declaring a physical read replica ready. Do not assume every unlogged hint modification on a primary is individually replicated. WAL-logged VM changes and frozen state have different persistence semantics from hints. Standby-local dirtying was not measured in this campaign.

## Should we add FREEZE?

**Consider it for large, stable tables or archival partitions that will remain mostly unchanged. Do not make it a universal post-restore requirement.**

FREEZE lowers the age thresholds for aggressive freezing, subject to transaction-visibility safety. It can establish frozen state while we already have a maintenance window, reducing future revisits to unchanged all-frozen pages. It can also add present CPU, I/O and WAL work. Its benefit shrinks if the data will soon be updated or deleted. Long-running transactions can limit what can safely be frozen.

A logical reload creates tuples with destination transaction IDs; source data age does not make those new tuples immediately old for wraparound purposes. The rationale for early FREEZE is planned future maintenance cost, not an automatic emergency after restore.

**Ordinary VACUUM is enough to aim for all-visible coverage; FREEZE is not an extra prerequisite for Index Only Scans.** Ordinary vacuum may already freeze tuples opportunistically, so inspect actual all-frozen coverage before assuming an extra FREEZE pass helps. [VACUUM FREEZE semantics](https://www.postgresql.org/docs/19/sql-vacuum.html), [freezing guidance](https://www.postgresql.org/docs/19/routine-vacuuming.html#VACUUM-FOR-WRAPAROUND).

The [October 20 follow-up](forge-oct20-followup.md) now compares initial maintenance with a later forced aggressive vacuum. On PG18.6, VACUUM ANALYZE versus VACUUM (FREEZE, ANALYZE) took 3.28 versus 3.50 seconds initially; the later accounts pass took 2.78 versus 0.026 seconds. PG19rc1 ordinary VACUUM already froze the same 172,414 pages. This strengthens the case for evaluating FREEZE during a stable-data restore window, but does not establish a universal winner. Each arm ran once; initial maintenance was database-wide, the later command targeted one table, and WAL figures are cluster LSN deltas. The later pass used zero age thresholds, not actual XID aging. The PG19 cause remains unisolated.

## Spoken version

“After restore we need good estimates, cheap visibility checks, and eventually safe frozen state. ANALYZE, VACUUM and FREEZE address different parts. A read replica cannot build PG19's VM locally, but it can still do hint-bit work. So read-only does not mean physically inert—and FREEZE is a lifecycle decision, not a requirement for every fast read.”
